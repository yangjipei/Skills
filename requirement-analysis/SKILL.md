# 需求分析

先读[阶段产物与交接协议](../_shared-requirement-protocol.md)，再按任务读取[需求分析工作流](references/workflow-analysis.md)。

## 职责

- 接受原始需求、已登记诉求、已有材料或外部等效文档，不要求先执行 `business-request-registration`。
- 从业务问题与场景出发主动发现需求，不把“澄清用户已经说过的话”当作主要工作。
- 维护 `01-需求分析.md`：Fact Inventory、Scenario Discovery、Problem / Goal、Scope、Core Rules、Product Skeleton、流程图规划。
- 负责需求级 `Fxxx / Sxxx / Dxxx / Qxxx` 稳定编号。
- 判断后续业务 / 系统流程是否需要可视化，并给 `business-flow-html` 最小事实输入。
- 页面路径只做初步能力映射；详细 IA / Page Spec 交给 `prd-html-prototype`。
- 不写完整 PRD、不生成 HTML 原型、不做视觉设计。

## 核心原则

1. **先事实，后推导**：事实、假设、建议分离；无依据内容不写成事实。
2. **场景是核心中间层**：主动挖掘“谁，在什么触发下，为了完成什么任务，遇到什么问题，希望得到什么结果”。
3. **先扫描，后深入**：先建立场景清单，再只深入核心场景和会改变方案的关键分支。
4. **只问阻塞问题**：每轮优先 1～3 个会改变目标、范围、流程、账务、状态、权限、核心规则或页面结构的问题。
5. **产品骨架在本阶段收敛**：不额外创建 Product Skeleton Skill，避免重复读取与重复文档。
6. **场景不无限发散**：不会改变产品范围、流程、规则、对象、状态或页面结构的长尾场景只登记，不继续展开。
7. **下游最小交接**：优先交接 S/F/D/Q ID 与对应短句，不让下游重新阅读完整需求历史。

## 编号

- `Fxxx`：已确认事实
- `Sxxx`：需求场景
- `Dxxx`：已确认决策
- `Qxxx`：待确认问题

编号连续、不复用；相同事实或决策不重复保存；已解决 Q 从待确认列表移除，必要时由 D 引用来源 Q。

## 执行

1. 建立事实基线和原始诉求。
2. 分析业务背景、角色、任务、问题、影响、目标与价值。
3. 扫描需求场景，区分核心 / 关键分支 / 长尾和本期 / 非本期。
4. 对核心场景按六要素深入：`Actor + Trigger + Task + Problem + Expected Outcome + Constraints`。
5. 从场景推导本期范围、核心对象、关键状态、权限和关键规则。
6. 形成 Product Skeleton：核心能力与页面 / 模块初步映射，不展开普通字段和视觉细节。
7. 只保留真正阻塞后续方案的 Qxxx。
8. 判断业务 / 系统流程图需要，定义名称、起止边界、覆盖 Sxxx 和最小 F/D 输入。
9. 更新 `01-需求分析.md` 和最小续作索引；本阶段结束。

## 完成 Gate

满足以下条件即可进入业务流程阶段：

- Problem / Goal 可以清楚解释；
- 核心角色与核心 Sxxx 已识别；
- In Scope / Out of Scope 基本明确；
- 核心对象、状态与规则足以影响流程的部分已明确；
- Product Skeleton 可以解释“本期准备建设什么”；
- 阻塞问题已解决，或明确标记当前无法继续的 Qxxx；
- 已给出业务 / 系统流程的必要性判断和最小交接输入。

普通字段、列宽、颜色、Hover、视觉风格和页面微交互不是本阶段完成条件。

不读取 `_shared-wiki`，不自行修改公共经验。
