# PRD 编译与定稿

先读[阶段产物与交接协议](../_shared-requirement-protocol.md)，再读取[PRD 编译与终态交付](references/workflow-prd.md)及按需写作规则。

## 定位

默认情况下，PRD 是**已验证方案的结构化执行契约**，不是早期探索工具。

有页面的需求优先消费：

```text
01-需求分析.md
+ 已确认必要流程 / Flow Spec
+ 已确认 page-ia.md
+ 已确认 Prototype Spec
+ 原型相对链接
```

不通过重新阅读完整 HTML 来反推字段、规则和交互。

无页面需求可直接基于需求分析 + 必要流程编写；用户提供的外部等效确认材料也可独立作为输入，不强制补跑前序阶段。

## 执行

1. 建立本次 PRD Compilation Input：目标、范围、S/F/D、必要流程、页面 Spec 与链接，仅取当前文档章节需要的最小信息。
2. 使用标题索引和受影响章节并集生成 / 修订 PRD 工作稿；同一轮不重复读取已消费源。
3. 对页面功能，字段、操作、状态和交互以已确认 Prototype Spec 为主要页面事实源；HTML 只用于“界面原型”链接。
4. 对业务规则，优先使用需求分析的 F/D 与已确认流程，不把 UI-DERIVED 选择写成业务规则。
5. PRD 不新增产品能力。如果发现缺口：业务问题回 `requirement-analysis`，流程缺口回 `business-flow-html`，页面缺口回 `prd-html-prototype`。
6. 用户确认后成对固化当前终态；若明确要求产品评审，再交 `prd-product-review`。
7. 评审后的纯文档表达问题可直接修订；改变业务 / 流程 / 页面事实的问题先回责任基线，再只更新受影响 PRD 章节。

不修改需求分析、流程、原型或评审产物；不读取 `_shared-wiki`。
