# 产品流程 HTML 集成规则

判断流程图必要性、规划或生成业务、系统、页面流程时读取；独立 PRD 任务同样可使用本规则。

目标：向 `$business-flow-html` 只传递当前流程需要的内容，并向责任 Skill 交接需要回补的内容与链接。视觉、输出、校验和模板进化规则以该 Skill 为准，本文不重复定义。

## 1. 流程类型与边界

产品流程分为三类，不得混用同一层语义：

1. **业务流程（按需）**：回答“业务为什么这样运转”，展示参与角色、业务阶段、关键判断、异常出口和业务结果。复杂多角色协作、关键判断或异常出口需要可视化时生成；简单线性流程可用文字表达，用户明确要求 HTML 时使用紧凑视图。
2. **系统流程（按需）**：回答“系统如何支撑业务运转”，在多系统分工、自动任务、状态流转、数据交接或异常补偿时生成；优先使用系统泳道、时序或状态视图。
3. **页面流程（按需）**：回答“用户如何通过页面完成操作”，在跨页、多步骤、关键弹窗／抽屉、多角色路径或明显失败恢复路径时生成；展示入口、页面节点、关键操作、系统反馈和结果，不复制字段规格。

字段说明、静态实体关系、配置项清单和数据字典不属于上述流程，优先使用 Markdown 表格或编号说明。

## 2. 流程图数量与拆分

每项需求先判断是否需要图。无需图时记录“不需要”及原因，不建空清单或强制执行流程 Skill。需要图时，由 `business-flow-html` 维护 `flows/流程清单.md`，记录总数、名称、类型、边界、场景、必要性、来源基线、文件链接及确认状态；澄清提供建议与事实，PRD 可直接提供等效输入。

- 图的数量由信息表达需要决定，不设每个需求至少一张的数量要求；无图也必须明确文字流程事实。
- 不按“业务／系统／页面”机械地各生成一张。系统流程和页面流程仅在命中其适用条件时加入。
- 一张图应能围绕一个可独立评审的目标，从明确起点走到明确结果。不同参与角色、触发方式或异常路径仍能在同一视图中清晰表达时不拆分。
- 当一张图跨越多个相互独立的业务场景、系统边界或用户任务，导致主线难以辨认时拆分；同一类型可以有多张。
- 若拆分方式会改变需求范围、系统职责或用户对方案的理解，先确认清单；否则说明数量判断后可直接生成全部工作稿。

## 3. 最小读取

调用 `$business-flow-html` 前，只提供当前流程真正需要的上下文：

1. PRD 前读取当前流程相关的共创决策和方案内容；PRD 后修改时读取受影响的 PRD／方案章节；
2. 当前有效决策；
3. 必要术语；
4. 已有流程图（如果用户提供）。

禁止为了画流程而全文读取整个 PRD，除非该流程确实跨越多个核心章节且无法局部判断。

## 4. Flow Spec

生成前先压缩成 Flow Spec，不要求单独落盘：

```text
Flow Name:
Flow Type: Business | System | Page
Goal:
Start:
End:

Actors / Lanes / Page Nodes:

Stages:
1. 阶段名称
   - Main steps
   - Decisions
   - Exit / Exception

2. ...

Key Rules:
- ...

Open Issues:
- ...
```

只保留会影响流程走向的内容，不复制大段 PRD。根据 Flow Type 只填写相应的角色、系统泳道或页面节点，不强行兼有三者。

## 5. 确认、PRD 引用与回补

本次必要流程生成后交用户确认，清单维护实际状态。只有相关交付确实依赖的必要图尚未确认时，才阻塞该交付；不因为没有执行前序 Skill、没有指定清单文件或无需绘图而阻塞。用户反馈影响数量或边界时，只更新受影响流程与清单。

定义缺失时先提出最小问题；需要修订方案或 PRD 时交给对应责任 Skill，流程 Skill 不改这些文档。独立调用交付缺口说明，已有串联授权时继续交接。确认后的图固化到 `flows/最终确认版/`，重开再次确认后替换同名终态。PRD 链接由 `prd-writing` 维护。

PRD 正文仍需保留可独立理解的流程说明，可增加相对链接：

```markdown
[查看交互式产品流程](../flows/最终确认版/strategy-orchestration-business-flow.html)
```

不要用“详见 HTML”替代正文关键规则。PRD 以已确认的流程事实为基线；需要图时引用确认图，不需要图时保留可独立理解的文字流程说明。
