# 建档、共创、流程确认与方案确认

仅在新需求建档、需求探索、流程规划确认或方案确认时读取。

## 1. 收件箱与建档

处理新需求前，必须逐一检查 `02_Inbox/` 的全部材料并判断与当前需求的相关性，但不默认将全部文件正文输入模型。按以下顺序读取：

1. 先列出文件名、类型、大小和修改时间，排除 `.DS_Store` 和明确的派生文件。
2. Markdown 使用 `python3 .agents/scripts/markdown_sections.py <文件>` 查看标题及行号；根据当前需求关键词，用多个 `--select` 一次批量提取相关章节。
3. 非 Markdown 先读可搜索的文档元数据、目录或文本提取结果，再定位相关页或区域。
4. 只有索引、元数据和局部内容无法判断相关性，或用户要求整体理解某份材料时，才读取该文件全文。

相关材料保留原文件名，迁入：

`03_Requirements/进行中/REQ-YYYYMMDD-NNN-需求名称/参考资料/`

不相关材料继续留在收件箱。需求名称由用户确认；编号使用首次提出日期和当日流水号。按需创建：

```text
00-需求信息.md
01-需求共创记录.md
02-方案确认.md
03-PRD/
04-评审记录/
prototype/
flows/
参考资料/
```

没有内容的文件和目录可延迟创建。状态按实际阶段更新：

`需求探索中 → 流程规划中 → 流程图待确认 → PRD编写中 → PRD待确认 → 专项评审中 → PRD修订中 → 原型生成中 → 原型待确认 → 待归档确认 → 已归档`

`00-需求信息.md` 中维护以下可覆盖更新的最小续作索引：

```markdown
## 续作索引

- 当前目标：
- 当前阶段／下一动作：
- 阻塞问题：无／Qxxx
- 当前有效基线：`相对路径`
- 本轮受影响范围：
- 按需读取入口：`相对路径#章节`
```

- 基线可指向当前方案、PRD、流程或原型 Spec；只列实现当前目标必需的入口，不列历史文件清单。
- 目标、阶段、下一动作、阻塞点、基线或影响范围变化时才更新；不按每轮对话追加摘要。
- 当前会话已持有完成下一动作的充分上下文时，不为“可能会重启”额外写文档。

## 2. 轻量共创

1. 先确定目标、范围、业务流程、系统职责和会改变方案的核心规则。
2. 每轮优先询问 1～3 个关联的阻塞问题；可安全推导且无冲突的内容不重复确认。
3. 页面功能必须确认完整菜单路径及新增／修改／复用方式。
4. 仅在金额、账务、状态、时间、优先级、权限、幂等或重大异常有歧义时用具体场景验证。
5. 普通字段和交互留到 PRD 编写，不在早期逐项盘问。

仅在用户要求保存、阶段切换、重要决策变化或需要恢复点时更新 `01-需求共创记录.md`：

```markdown
## 已确认决策
| 编号 | 结论 | 依据／备注 |

## 待确认问题
| 编号 | 问题 | 建议（可选） | 影响 | 阻塞性 |

## 范围外事项
```

- 决策使用 `D001` 起的连续编号；未决问题使用 `Q001` 起的连续编号，编号不复用。
- 用户采纳建议后只保留完整决策，不重复保存确认原话和规则副本。
- 已解决问题从待确认表移除；必要时在决策备注中写 `来自 Qxxx`。
- 不记录逐轮时间、完整聊天、重复摘要或助手推理。

## 3. 探索顺序

按依赖推进；前一层仍有阻塞问题时不深入后一层：

1. 背景、用户、问题、目标和价值；
2. 国家、产品、客群、角色、权限、本期／非本期范围和术语；
3. 能力结构、业务流程、系统边界、核心对象／状态和关键规则；
4. 端型、完整路径、页面／无页面、新增／修改／复用及上下游依赖；
5. 字段、交互、规则、异常和验收；
6. 指标、权限、数据、上下游及多国家一致性。

框架阶段使用一张紧凑表即可：

| 端型 | 路径／模块 | 功能 | 页面组成 | 建设方式 | 角色 |
| --- | --- | --- | --- | --- | --- |

共同探讨无阻塞问题后，所有正式需求都必须完成“产品流程”判断：

1. **业务流程（必须）**：表达业务为什么这样运转，突出角色、业务阶段、关键判断和业务结果，不用后台实现步骤代替业务语义。
2. **系统流程（按需）**：当需求包含多系统分工、自动任务、状态流转、数据交接或异常补偿时生成，表达系统如何支撑业务运转。
3. **页面流程（按需）**：当用户需跨页、跨步骤，或通过弹窗／抽屉完成关键任务时生成，表达用户如何通过页面完成操作及获得反馈。

判断不能只记录三类流程“是否需要”，还要形成流程图清单，明确总数、每张图的名称、类型、覆盖范围和判断依据。同一类型可按独立业务场景、系统边界或用户任务拆成多张；不得为了凑数量拆分，也不得把语义层级不同或无法清晰评审的内容硬塞进一张图。流程的数量判断、输出形式和生成规则见 `business-flow-integration.md`。

## 4. 流程规划与确认

1. 先向用户给出流程图清单：总数，以及每张图的名称、类型、范围和必要性。若拆分方式会改变需求范围或方案理解，先确认清单；否则可说明判断后直接生成。
2. 按清单使用 `$business-flow-html` 生成 `flows/workdraft/` 下的全部流程图，不要求用户再次指定 HTML 输出形式。
3. 将全部流程图逐一交用户确认。确认重点是角色与边界、主路径、关键判断、异常出口、系统职责或页面跳转是否准确，不在此阶段展开普通字段规格；同时明确告知用户，确认全部流程图及方案后即进入 PRD 编写。
4. 用户补充或否定时，回到共同探讨并只更新受影响的方案与流程图。若新增、删除或重拆流程图，同步更新清单和总数。
5. 所有清单内的流程图及方案获得用户明确确认后，视为方案确认和 PRD 编写授权；部分确认不得视为完成前置闸门，也不得重复再询问一次 PRD 授权。

## 5. 方案固化与进入 PRD

目标、范围、系统职责、核心规则和功能边界已确定，且清单内流程图全部确认后，生成 `02-方案确认.md`，只包括：

- 业务目标与适用范围；
- 已确认流程图清单：总数、名称、类型、范围、判断依据和相对链接；
- 系统职责；
- 核心规则和关键异常；
- 本期／非本期范围；
- 功能清单；
- 非阻塞待确认问题。

固化后直接进入 PRD 编写并创建工作稿。用户在确认前补充或否定时回到共创或流程确认，不记录确认原话副本；未确认全部流程图及方案不得创建 PRD 工作稿。
