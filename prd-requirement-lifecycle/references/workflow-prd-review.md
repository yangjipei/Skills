# PRD、评审与产品流程维护

只读取当前任务对应部分；业务、系统和页面流程的具体生成与维护规则另见 `business-flow-integration.md`。准入与串联范围遵循[共享协议](../../_shared-requirement-protocol.md)，保存目录不增加前置阶段。

## 1. PRD 工作稿与终态交付

由 `prd-writing` 执行：用户已要求编写 PRD，且目标、范围、功能、规则及必要流程事实充分并已确认时创建工作稿。输入可以是方案产物或用户提供的等效材料，仅判断为必要的图须确认。不存在工作稿时运行：

`sh .agents/skills/prd-requirement-lifecycle/scripts/create_prd_workdraft.sh <需求目录>/03-PRD/PRD-工作稿.md`

脚本一次复制 `06_Templates/PRD骨架.md` 与 `06_Templates/PRD补充信息骨架.md`，生成 `PRD-工作稿.md` 和同目录的 `PRD补充信息-工作稿.md`；任一目标已存在时均不创建，避免只生成其中一份。主 PRD 仅含第 1～6 章；第 7～11 章只写入独立补充信息文档。根据当前编写范围，通过 `prd-writing-rules.md` 只读取对应规则。

修改已有 PRD 时：

1. 用 `python3 .agents/scripts/markdown_sections.py <PRD路径>` 获取标题、行号和 SHA256，不先读正文；
2. 结合当前有效方案或用户提供的等效确认输入、必要流程事实，确定全部受影响章节的并集；
3. 用一次命令的多个 `--select` 批量提取该并集。规则、异常、权限、指标或验收发生变化时，只追加主 PRD 与补充信息中其明确依赖章节；
4. 仅在整体重写、全局定稿、变化跨多个核心流程或无法从索引判断影响时读取全文。同一轮修订中已提取的章节不得因编写、评审或校验分阶段而重复读取。

编写要求：

- 页面功能定义路径、组成、字段、操作、状态反馈、权限、规则和验收；
- 每个页面的“界面原型”章节只包含“查看 XXXX 界面原型”链接和按页面实际区域拆分的多张字段说明表，不写界面结构摘要，不为字段说明另设子章节；使用“**查询条件字段说明**”“**列表字段说明**”“**新增／编辑字段说明**”等加粗分组名，复杂配置、详情或监控页面按实际区域命名；同一字段用于不同区域时允许重复并分别定义区域交互；每张表固定为 `字段｜类型｜字段说明｜交互规则` 四列，不得增加其他列；类型写控件或展示类型，必填、来源或枚举、默认值、校验、联动、只读和禁用条件按实际需要合并写入交互规则，未知内容标为待确认；
- 业务规则先按实际类别设置小标题，再写可判断、可执行、可验证的规则；
- 无页面功能定义输入、输出、系统处理、依赖、权限和异常；验收标准仅在独立的 `PRD补充信息` 文档中维护；
- 不用“详见原型”替代关键定义。

版本与留存遵循共享协议：维护一对工作稿，用户确认后成对固化唯一终态，再次确认前保留旧终态；清理前单独确认。独立编写不强制评审；用户已要求包含评审的串联任务时，工作稿交 `prd-product-review`，由 `prd-writing` 完成必要修订后再请求最终确认。

PRD 阶段交付后停止。只有已有串联授权时才继续评审、原型等阶段，不把内容确认视为新增执行授权。

## 2. 专家评审

由 `prd-product-review` 执行。接受用户指定的工作稿、最终稿或外部 PRD，不以先执行编写或确认阶段为前提。只做产品专家评审；在既有需求信息中维护评审状态，输出到 `04-评审记录/产品专家评审.md`。缺少补充信息时说明可审范围与缺口，不强制先生成文档。

产品专家评审只获得标题索引、必要决策，以及主 PRD 的目标、范围、流程、相关功能、字段完整性与交互，和补充信息中的指标、影响与待确认问题。

### 产品专家审核输出

产品专家仅检查：目标是否成立、流程是否闭环、规则是否明确、方案是否合理、是否存在关键完整性缺口。不得复述原需求、重写流程、展开无问题内容、输出技术实现细节或低价值建议。

最终评审输出必须且仅按以下八部分组织；表格逐项填写。无问题的检查项明确写“无关键问题”，不省略标题、字段或表格行。普通需求控制在 800～1500 字，复杂需求不超过 2500 字。

### P2 表达优化

只在发现明确的跨章节依赖时补充章节。评审时合并重复意见和冲突，并对受影响章节及交叉引用做一致性检查；无法判断时才读全文。

每条有效意见只记录位置、问题、影响／严重程度、建议和处理结论：

- 阻塞：不解决不能定稿；
- 重要：需解决或明确接受风险；
- 建议：不影响本期交付。

会改变业务或实现口径的意见在本评审结果中记录并交用户确认；需要纳入共创决策时交给 `requirement-clarification`。全部 PRD 修订（包括文字、格式和编号）交给 `prd-writing`，评审 Skill 不直接修改原文。修订影响产品专家已提出的问题、相关流程、规则、异常或验收条件时，由产品专家复审；纯文字格式无需复审。

完成本次检查后交付评审结论，存在阻塞问题也可完成“评审任务”，但不得标为“评审通过”。修订内容未复审时标为待复审，不沿用旧基线结论。独立评审不自动修改或最终确认 PRD；已有串联授权时交给 `prd-writing` 处理修订和用户最终确认。

## 3. 产品流程维护与交接

- 每项需求判断图的必要性；不需要图时用文字定义流程，不增加绘图阶段。
- 必要图由 `business-flow-html` 生成、校验、确认并固化到 `flows/最终确认版/`；工作稿放 `flows/workdraft/`。
- `prd-writing` 维护 PRD 中的独立流程说明及相对链接，不写入流程 HTML。
- 发现流程与 PRD 冲突时暂停受影响内容，说明需要调整的事实与责任产物；按当前授权范围交接并重新确认，不无差别重做全部流程。
