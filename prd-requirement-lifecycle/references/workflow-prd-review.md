# PRD、评审与产品流程维护

只读取当前任务对应部分；业务、系统和页面流程的具体生成与维护规则另见 `business-flow-integration.md`。首次 PRD 编写前，方案与清单内全部流程图必须已获用户确认。

## 1. PRD 工作稿与终态交付

方案与清单内全部流程图已确认后，按流程确认时已说明的约定直接运行，无需再次询问 PRD 授权：

`sh .agents/skills/prd-requirement-lifecycle/scripts/create_prd_workdraft.sh <需求目录>/03-PRD/PRD-工作稿.md`

脚本一次复制 `06_Templates/PRD骨架.md` 与 `06_Templates/PRD补充信息骨架.md`，生成 `PRD-工作稿.md` 和同目录的 `PRD补充信息-工作稿.md`；任一目标已存在时均不创建，避免只生成其中一份。主 PRD 仅含第 1～6 章；第 7～11 章只写入独立补充信息文档。根据当前编写范围，通过 `prd-writing-rules.md` 只读取对应规则。

修改已有 PRD 时：

1. 用 `python3 .agents/scripts/markdown_sections.py <PRD路径>` 获取标题、行号和 SHA256，不先读正文；
2. 结合 `02-方案确认.md`、当前有效决策和已确认流程图清单，先确定全部受影响章节的并集；
3. 用一次命令的多个 `--select` 批量提取该并集。规则、异常、权限、指标或验收发生变化时，只追加主 PRD 与补充信息中其明确依赖章节；
4. 仅在整体重写、全局定稿、变化跨多个核心流程或无法从索引判断影响时读取全文。同一轮修订中已提取的章节不得因编写、评审或校验分阶段而重复读取。

编写要求：

- 页面功能定义路径、组成、字段、操作、状态反馈、权限、规则和验收；
- 每个页面的“界面原型”章节只包含“查看 XXXX 界面原型”链接和按页面实际区域拆分的多张字段说明表，不写界面结构摘要，不为字段说明另设子章节；使用“**查询条件字段说明**”“**列表字段说明**”“**新增／编辑字段说明**”等加粗分组名，复杂配置、详情或监控页面按实际区域命名；同一字段用于不同区域时允许重复并分别定义区域交互；每张表固定为 `字段｜类型｜字段说明｜交互规则` 四列，不得增加其他列；类型写控件或展示类型，必填、来源或枚举、默认值、校验、联动、只读和禁用条件按实际需要合并写入交互规则，未知内容标为待确认；
- 业务规则先按实际类别设置小标题，再写可判断、可执行、可验证的规则；
- 无页面功能定义输入、输出、系统处理、依赖、权限和异常；验收标准仅在独立的 `PRD补充信息` 文档中维护；
- 不用“详见原型”替代关键定义。

版本与留存规则：

- 需求进行中只保留一对 `PRD-工作稿.md` 与 `PRD补充信息-工作稿.md`；评审或反馈直接更新这对工作稿，不新增中间版本。
- 用户最终确认后，将工作稿成对固化为唯一终态文件：`PRD-最终确认版.md` 与 `PRD补充信息-最终确认版.md`；若需求重开后再次最终确认，以新终态替换旧终态，不保留历史版本。
- 固化完成后删除对应工作稿，以及不再被当前终态引用的流程工作稿和历史流程目录。删除前须获得用户对过程材料清理的明确确认。
- 不创建 `v0.x`、`v1.x`、原型反馈或评审修订等过程版本目录；版本演进仅在需求进行中通过工作稿体现。

## 2. 专家评审

用户确认 PRD 内容后，默认只完成产品专家评审。业务、技术、测试或其他专项评审仅在用户明确指定时加入；不得因需求重开、版本升级或影响面较大自动扩大评审范围。把约定范围写入 `00-需求信息.md`，评审记录只说明本次实际范围；完成条件以双方约定的评审范围为准。

每类评审只获得标题索引、本专业必要决策和相关章节：

- 业务：背景、范围、现状、方案、相关业务规则、异常和影响；
- 产品：主 PRD 的目标、范围、流程、相关功能、字段完整性与交互，以及补充信息中的指标、影响和待确认问题；
- 技术：主 PRD 的方案、相关功能与规则，以及补充信息中的异常和影响；
- 测试：主 PRD 的范围、相关功能与规则，以及补充信息中的异常和验收。

### 产品专家审核输出

产品专家仅检查：目标是否成立、流程是否闭环、规则是否明确、方案是否合理、是否存在关键完整性缺口。不得复述原需求、重写流程、展开无问题内容、输出技术实现细节或低价值建议。

最终评审输出必须且仅按以下八部分组织；表格逐项填写。无问题的检查项明确写“无关键问题”，不省略标题、字段或表格行。普通需求控制在 800～1500 字，复杂需求不超过 2500 字。

- 流程／业务规则变化：业务、产品；
- 系统职责／状态／接口／数据变化：技术；
- 验收／异常／边界变化：测试；
- 纯文字格式：无需复审。

约定评审、必要复审和口径问题均完成后，请用户最终确认 PRD：

- 用户确认后成对固化主 PRD 与补充信息至唯一的终态文件；
- 不需要页面原型时，状态直接更新为“待归档确认”；
- 需要页面原型时，进入“原型生成中”，按 `workflow-prototype.md` 继续；
- 已被 PRD 引用的产品流程 HTML 在 PRD 编写前已完成用户确认；若 PRD 修订影响流程，须重新完成轻量校验和用户确认，再固化到终态流程目录。

## 3. 产品流程可视化

每个正式需求的流程图清单和工作稿应在 PRD 编写前完成并确认。PRD 阶段读取 [business-flow-integration.md](business-flow-integration.md)，只处理终态固化或因 PRD 修订产生的受影响流程，不重新无差别生成全部流程图。

- 工作稿：`flows/workdraft/<flow-slug>.html`，允许覆盖同名工作稿；
- 固化版：`flows/最终确认版/<flow-slug>.html`；需求重开并再次确认后，以新的终态文件替换原文件，不保留历史流程目录。
- PRD 正文仍需独立说明实际适用的关键流程和规则，并引用已确认流程图；
- PRD 编写发现已确认流程存在遗漏或冲突时，暂停受影响内容，回到方案与流程确认；更新并确认流程图后再继续 PRD；
- PRD 修订改变流程走向、边界或职责时，只更新受影响流程图，并重新确认 PRD 与流程图的一致性。
