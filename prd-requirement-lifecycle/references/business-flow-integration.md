# 产品流程 HTML 集成规则

在正式需求中规划或生成业务、系统、页面流程时读取。

目标：向 `$business-flow-html` 只传递当前流程需要的内容，并处理 PRD 回补和链接。视觉、输出、校验和模板进化规则以该 Skill 为准，本文不重复定义。

## 1. 流程类型与边界

产品流程分为三类，不得混用同一层语义：

1. **业务流程（必须）**：回答“业务为什么这样运转”，展示参与角色、业务阶段、关键判断、异常出口和业务结果。简单线性流程也要保留，但应使用紧凑视图，不为凑阶段而复杂化。
2. **系统流程（按需）**：回答“系统如何支撑业务运转”，在多系统分工、自动任务、状态流转、数据交接或异常补偿时生成；优先使用系统泳道、时序或状态视图。
3. **页面流程（按需）**：回答“用户如何通过页面完成操作”，在跨页、多步骤、关键弹窗／抽屉、多角色路径或明显失败恢复路径时生成；展示入口、页面节点、关键操作、系统反馈和结果，不复制字段规格。

字段说明、静态实体关系、配置项清单和数据字典不属于上述流程，优先使用 Markdown 表格或编号说明。

## 2. 流程图数量与拆分

共同探讨完成后，先形成流程图清单，再生成图。清单至少包括：总数、流程名称、流程类型、起止边界、覆盖场景和需要该图的原因。

- 每个正式需求至少一张业务流程图；简单线性流程使用一张紧凑视图即可。
- 不按“业务／系统／页面”机械地各生成一张。系统流程和页面流程仅在命中其适用条件时加入。
- 一张图应能围绕一个可独立评审的目标，从明确起点走到明确结果。不同参与角色、触发方式或异常路径仍能在同一视图中清晰表达时不拆分。
- 当一张图跨越多个相互独立的业务场景、系统边界或用户任务，导致主线难以辨认时拆分；同一类型可以有多张。
- 若拆分方式会改变需求范围、系统职责或用户对方案的理解，先确认清单；否则说明数量判断后可直接生成全部工作稿。

## 3. 最小读取

调用 `$business-flow-html` 前，只提供当前流程真正需要的上下文：

1. PRD 前读取当前流程相关的共创决策和方案内容；PRD 后修改时读取受影响的 PRD／方案章节；
2. 当前有效决策；
3. 必要术语；
4. 已有流程图（如果用户提供）。

禁止为了画流程而全文读取整个 PRD，除非该流程确实跨越多个核心章节且无法局部判断。

## 4. Flow Spec

生成前先压缩成 Flow Spec，不要求单独落盘：

```text
Flow Name:
Flow Type: Business | System | Page
Goal:
Start:
End:

Actors / Lanes / Page Nodes:

Stages:
1. 阶段名称
   - Main steps
   - Decisions
   - Exit / Exception

2. ...

Key Rules:
- ...

Open Issues:
- ...
```

只保留会影响流程走向的内容，不复制大段 PRD。根据 Flow Type 只填写相应的角色、系统泳道或页面节点，不强行兼有三者。

## 5. 确认、PRD 引用与回补

清单内全部工作稿生成后，逐一交用户确认。部分流程已确认而其他流程仍待确认时，保留确认状态，但不得进入 PRD 编写。用户反馈影响流程数量或边界时，先更新清单，再只重生成受影响流程。

流程图在 PRD 前暴露定义不足时，回到共同探讨或方案并重新确认受影响流程；PRD 编写或修订后暴露不一致时，修订 PRD 与受影响流程，并重新确认二者。

PRD 正文仍需保留可独立理解的流程说明，可增加相对链接：

```markdown
[查看交互式产品流程](../../flows/v1.0-最终确认版/strategy-orchestration-business-flow.html)
```

不要用“详见 HTML”替代正文关键规则。PRD 必须以已确认流程图为基线，并保留可独立理解的关键流程说明。
